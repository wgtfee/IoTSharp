### 1. 授权与审计约束

- 新审核入口 POST /api/pdm/p2/reviews/{id}/decision：仅允许签名 JWT 的 PdmReviewApprover 角色；Tenant/Customer/UserId 必须从可信令牌读取，不能由客户端填写。
- 除已有 P1/P2 发布门禁，还要求 P2:ReviewWriteEnabled、P2:ReviewSchemaReady 和 P2:IamMappingApproved 显式开启，默认全为 false。
- 真实本地 Kestrel/JWT 回归覆盖未登录 401、未授权角色 403、无效令牌 401、跨租户 404、自己审批自己的草稿被拒、重复/过期 Revision 409、成功后记录审核审计。
- 通过时仅返回 ApprovedForPlanning：意味着可以进入后续规划，绝不意味着工单创建、外部通知发送、PLC/MES 操作成功。
- 还需真实 IAM 将角色安全绑定到已审核人员，并校验实际用户 ID 为 GUID；未批准时保持默认关闭。

### 2. 数据持久化与 schema

- 新的 PdmP2PolicyDbContext 与已有 PdmP2ReviewDbContext 均完全独立，不进入主 IoTSharp ApplicationDbContext 或自动迁移。
- 离线 V001 SQL 包：PdmP2Review、PdmP2ReviewAudit、PdmP2PolicyRevision、PdmP2PolicyAudit，共四表，生成 SQLite、SQL Server、PostgreSQL 三套初始建表草案与 SHA-256 清单。
- 三份 SQL 文件都已存在且重新计算 SHA-256，与清单完全匹配；无 DROP TABLE / ALTER DATABASE 破坏性命令。
- 这些属于版本化初始化 DDL 审查草案，不是已应用的生产迁移，也不代表真实 SQL Server/PostgreSQL 索引、锁/并发行为已验证；DBA 评审、备份和回滚方案仍必需。

### 3. 工单适配边界

- 只实现独立模拟 Transport 和内存 Outbox；重复演练使用受租户/客户/审核记录约束的同一关联键；失败达到上限后返回 CompensatedInMemory。
- IsExternalOrderCreated 始终 false；没有连接真实工单、没有发消息、没有真实网络认证/重试补偿和外部事务一致性。
- 模拟内存补偿不能代替持久化 Outbox、真实外部认证、幂等应答、重启恢复与生产跨副本去重。

## 三、P2 研发准入结论与 P3 路线

**P2 研发：可视为完成当前范围的隔离功能与自动化回归，并可以开始 P3 研发。**
**P2 生产：未就绪，不能启用 Worker、生产审批写入或真实工单执行。**

进入 P3 的建议路线（需与正式规划对齐）：

1. P3-0：对 P1/P2 事件时间、Point Key、设备类别、质量标签、工况和真实故障标签建立离线训练/评估数据契约，不依赖生产直接读写。
2. P3-1：从统计异常检测与可解释基线开始，做滑窗特征、数据漂移、误报/漏报及实验可复现性验证。仍不直接宣称故障概率和剩余寿命。
3. P3-2：以 Shadow 模式接入离线验证过的结果，记录误报率、校准与解释证据；生产门禁、设备安全和工单权限保持隔离。
4. P3-3：仅在有足量、经证实的故障标签后评估监督模型，真实 RUL/故障概率另行设立精度与安全准入标准。
