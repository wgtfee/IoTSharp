# IoTSharp 丝饼产线数字孪生 V3 实施验收报告

> 基线文档：`IoTSharp_丝饼产线数字孪生完整场景优化设计_V3.md`  
> 实施日期：2026-08-27  
> 验收结论：V3 的 P0 业务闭环、P1 可配置与诊断能力已经落地；真实 PLC 点表、现场节拍和资产模型属于投产联调输入，不在代码中伪造。

## 1. 改造结论

原来的包装线示例采用“50 个相同托盘沿整条路线匀速循环”的显示逻辑。这种实现可以演示 Three.js，但不能表达丝饼、丝车、托盘、机器人、桁架和码垛区之间的业务关系，也无法正确传播满位阻塞。

本次将它改造成分层数字孪生运行时：

1. **业务状态层是唯一真相**：丝饼、塑料托盘、丝车 Slot、工位任务、分段占用和码垛位置都由独立运行时对象管理。
2. **物流控制层负责运动许可**：托盘位置使用 `currentSectionId + sectionProgress`，跨段必须通过容量检查、预占和原子转移。
3. **设备任务层负责工艺动作**：机器人和桁架只有在任务创建后才运动，完成时提交载具关系和工位状态。
4. **Three.js 只负责显示**：渲染层读取快照，不反向修改业务状态；载具切换使用 `Object3D.attach` 保持世界坐标连续。
5. **场景配置和资源绑定进入数据库**：草稿、路线、对象/Device 绑定、发布版本和版本快照沿用 IoTSharp 现有持久化链路。

## 2. 场景业务闭环

```text
丝车 Slot -> 旋转台定位 -> 上料机器人取丝饼 -> 绿色塑料托盘
    -> 分段辊道 -> PLC/仿真规则选择 A/B 支路 -> 汇流
    -> 桁架取丝饼 -> Stack-A 固定格位
    -> 空托盘回流 -> 上料工位 -> 下一生产周期
```

默认场景包含 50 个绿色塑料托盘、24 丝饼/车、13 个可计容 Section、A/B 分叉与汇流、上料机器人、旋转台、丝车、桁架和持久可见的码垛区。纸箱和木托盘语义已从新模板删除。

### 2.1 核心状态归属

| 实体 | 关键状态 | 唯一写入者 |
| --- | --- | --- |
| SilkCake | 当前载具、批次、质量、堆垛位置 | `SilkMaterialRuntime` |
| PlasticPallet | 当前 Section、进度、等待原因、丝饼、循环次数 | `PalletFlowController` |
| SilkCart / Slot | 当前取料位、剩余数量、更换状态 | `SilkMaterialRuntime` |
| Section | 占用、预占、容量、阻塞状态 | `TwinMaterialFlowRuntime` |
| Loading/Gantry Station | idle/waiting/processing/completed/fault | `ProcessStationManager` |
| Robot/Gantry Task | 任务阶段、进度、源/目标载具 | 对应设备 Controller |
| Stack-A | 行、列、层、容量、下一个格位 | `StackAreaManager` |
| Three.js Object3D | 位置、旋转、父子关系 | `ProceduralSilkCakeLine` 只读投影 |

## 4. 关键控制规则与不变量

### 4.1 跨段原子性

托盘到达 Section 末端后不会直接修改目标 Section。运行时先选择下一段，再执行目标容量检查和 reservation，最后原子提交源段释放与目标段占用。失败时托盘保持 `progress = 1`，记录结构化等待原因，下一个固定步长继续尝试。

必须始终成立：

```text
occupancy(section) + reserved(section) <= capacity(section)
同一托盘最多占用一个 Section
同一丝饼最多属于一个 Carrier
同一码垛格最多提交一次
没有任务时机器人和桁架不得产生工艺运动
```

### 4.2 分流优先级

1. PLC 模式读取现场信号并匹配规则；没有有效信号时等待，不能擅自分流。
2. Simulation 模式按 `payload.routeCode` 匹配规则；无匹配规则时采用场景配置的默认支路。
3. 选路只回答“去哪”；目标段无容量时依然不得进入。

### 4.3 上料守卫

只有以下条件同时满足才创建机器人任务：

- 上料 Section 内存在空托盘且到达工位；
- 丝车存在可用丝饼 Slot；
- 旋转台已经定位并锁定到目标 Slot；
- 上料工位未被其他任务占用；
- 托盘没有已有丝饼。

### 4.4 码垛守卫

只有以下条件同时满足才创建桁架任务：

- 桁架 Section 内存在满载托盘且到达工位；
- Stack-A 有可预占格位；
- 桁架工位空闲；
- 丝饼仍归属于该托盘。

Stack-A 满后不丢件、不穿透，也不让满载托盘变成空托盘；等待会沿 Section 容量自然向上游传播。

## 5. 数据库持久化合同

工作台保存不是仅写浏览器内存。保存草稿时后端先规范化和验证 V3 manifest，然后在同一场景聚合内更新：

| 数据 | SQL Server 持久化位置 |
| --- | --- |
| 完整场景、程序化 preset、仿真参数 | `DigitalTwinScenes.DraftPayload` |
| 路线点、Section、容量、分叉规则 | `TwinRoutes` |
| 对象/节点与 Device 遥测、属性、在线状态绑定 | `TwinObjectBindings` |
| 发布时不可变 manifest | `DigitalTwinSceneVersions.Manifest` |
| 发布路线与绑定快照 | 带 `SceneVersionId` 的路线/绑定记录 |

后端 `TwinManifestInspector` 已增加 `silk-cake-line`、托盘数量和仿真参数范围校验。程序化场景对象也参与资源草稿检查；点击运行态托盘/丝饼时不会被误认为模型根节点，因此不会产生错误的数据库绑定。

## 6. 自动验收结果

### 6.1 满位与阻塞场景

- 配置：50 托盘，Stack-A 容量 2。
- 结果：24 个托盘在线、26 个留在 SourceQueue；机器人完成 25 次，桁架完成 2 次；Stack-A 为 `2/2 full`；7 个托盘进入可解释等待。
- 断言：所有 Section 均满足 `occupancy + reserved <= capacity`；暂停后托盘位置保持不变。

### 6.2 空托盘闭环场景

- 配置：8 托盘，扩大 Stack-A 容量。
- 结果：SourceQueue 清空；机器人完成 50 次，桁架完成 47 次；单托盘最大完成 6 个生产循环。
- 断言：空托盘成功回流并再次上料，返回托盘不会被持续注入的新托盘饿死。

### 6.3 构建结果

```text
前端 production build：PASS（4088 modules transformed）
后端 dotnet build：PASS（0 errors）
V3 业务 smoke：PASS
```

后端构建仍报告仓库既有的 NuGet 安全公告和 nullable/API analyzer 警告；它们不是本次改造引入，但投产前应单独安排依赖升级窗口。

## 7. 现场投产前仍需输入的内容

以下内容不能用演示数据冒充完成，需要现场资料才能闭环：

1. **PLC 点表和握手时序**：分叉命令、到位、占用、故障、复位、命令确认以及超时策略。
2. **实测节拍和尺寸**：机器人/桁架动作时间、辊道速度、光电间距、丝车 Slot 数、托盘和丝饼实际尺寸。
3. **正式 GLB 资产**：当前程序化模型适合控制联调和功能验收；正式视觉交付应替换为经过减面、材质合批和 LOD 处理的设备模型。
4. **服务端权威仿真与 MCP 查询**：当前业务仿真在前端工作台运行；如需无人值守仿真、历史回放或 AI/MCP 跨会话查询，应把同一状态机迁移/复用到服务端 Runtime，而不是从 Three.js 反查状态。

这些是清晰的投产边界，不影响当前 V3 场景在工作台内的完整运行、编辑、保存、发布和诊断。

## 8. 操作验收步骤

1. 打开“数字孪生工作台”，新建或选择场景。
2. 点击工具栏“50托盘丝饼线”，确认替换当前草稿。
3. 在仿真参数中设置丝车容量、设备节拍和堆垛规格。
4. 点击“保存草稿”，再刷新页面，确认场景、路线和配置可以从数据库恢复。
5. 点击“运行”，观察 SourceQueue 释放、上料、A/B 分流、汇流、码垛和空托盘回流。
6. 点击托盘、丝饼、丝车、机器人、桁架或 Stack-A，在右侧查看当前业务快照。
7. 将 Stack 层数临时设小，验证 Stack Full 后上游逐段等待；重置或增大容量后验证恢复。
8. 绑定真实 Device 信号后切换 PLC 路由模式，验证“PLC 选路、容量放行”的控制边界。
